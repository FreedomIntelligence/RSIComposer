## 初审确认的问题（修复前）

### F01 · P2：共享 Feedback 允许非有限指标，持久交付会反复失败

位置：[feedback.py:25](../../src/rsisys/loops/contracts/feedback.py#L25)。

`Feedback.__post_init__` 检查终态枚举、错误和采纳 ID，但未检查 `quality_metrics`、`training_metrics`、`execution_metrics` 中的数值是否有限。自定义 exploration/handler 因而可以构造携带 `NaN` 或 `Infinity` 的 completed Feedback；`ExplorationProgress` 复用同一校验，也会接受它。

默认 decision harness 在交付时先将完整反馈写入持久 memory，再更新 completed/outstanding 状态。JSON 持久化拒绝非有限浮点数，导致交付报错，原指令继续 pending。重送同一回执仍报相同错误。

CPU 复现使用临时 `Application`，不调用模型或训练：

| 指标 | Feedback 构造 | 首次交付 | 重送 | 交付后的 pending / completed |
| --- | --- | --- | --- | --- |
| `0.5` | 接受 | 成功 | 幂等成功 | false / 1 |
| `NaN` | 接受 | ValueError | 同一 ValueError | true / 0 |
| `Infinity` | 接受 | ValueError | 同一 ValueError | true / 0 |

错误为 `Out of range float values are not JSON compliant`。这不是以前内置 evaluator 的同一实现缺陷：内置 [evaluation/__init__.py](../../src/rsisys/loops/exploration/harness/evaluation/__init__.py) 已有有限数值检查；此次确认的是公共 Feedback 边界仍允许其他执行实现绕过该保护。

建议：共享指标契约统一要求字符串键和有限实数值，并明确拒绝 bool 等非指标值。适配器在提交终态回执前，将不合法后端结果转成可持久化的失败回执，保留原始错误及证据引用。仅让接收端反复拒收同一 completed 回执，不能解决交付停滞；也不应把 NaN 默认为 0 或成功后静默丢弃指标。

验收：内置与自定义执行路径均覆盖三类指标；无效指标形成明确失败且可交付、可确认、可恢复；正常数值保持原值与来源。

### F02 · P2：OperationResult 接受字符串状态，随后记录阶段永久停滞

位置：[coordination.py:41](../../src/rsisys/loops/contracts/coordination.py#L41)，下游使用见 [engine.py:304](../../src/rsisys/loops/decision_making/harness/engine.py#L304)。

`OperationResult` 仅用枚举成员比较检查状态。`ExecutionStatus` 是字符串枚举，因此 `status='completed'` 也通过构造，以及执行器对 `__post_init__` 的再次校验。之后记录代码使用 `result.status.value`，对字符串触发 AttributeError。

CPU 复现：同一工具分别返回枚举和字符串状态。枚举返回正常 progressed；字符串返回在首步和重试时都抛出 `'str' object has no attribute 'value'`。工具执行次数和 policy 调用次数均保持 1，`pending_operation_record` 一直存在。实际操作已经执行，补写回执却无法结束，不能靠重新执行工具修复。

建议：与 Feedback 的严格枚举契约保持一致，在工具回执进入记账前拒绝错误状态类型；如需支持 wire JSON 字符串，集中在反序列化适配层转换。非法执行器回执应进入明确的失败记录，避免在部分写入后才发现类型错误。

验收：合法枚举成功；字符串/其他枚举状态按明确规则规范化或拒绝；无效回执不会留下无法 flush 的记录；恢复不重复执行已有副作用。

### F03 · P2：可选运行控制被 wrapper 变成必需能力，替换 harness 在首步失败

位置：[loop.py:46](../../src/rsisys/loops/decision_making/loop.py#L46)，调用方见 [runner.py:232](../../src/rsisys/runtime/runner.py#L232)。

`DecisionHarness` 只要求 `step/pending/receive_feedback`。更新运行提示属于可选能力，单独列在 `ResearchCycleDecisionEndpoint` 中。但 `DecisionMakingLoop` 总是暴露一个 callable `update_run_control`；底层 harness 没有实现时，这个 wrapper 抛出 NotImplementedError。Runner 以 wrapper 的 callable 存在性判断能力，在所有非默认 RunPolicy 下首步就调用它。

CPU 复现：同一个仅实现三项必需方法的 harness，默认策略可以执行一次 step；换成 `TimeRunPolicy(60)` 后，在首次决策之前报 `This decision harness does not support update_run_control`，harness step 调用次数为 0。此时尚未发生 finish 或研究重启，不能归因于缺少 restart 能力。

建议：将运行提示更新与研究重启分别发现和校验，wrapper 必须真实反映底层能力。没有可选提示接口时仍应能推进基础研究；需要重启的策略则在相应能力边界给出明确检查，不要在第一次决策时隐式失败。Host 截止和准入检查继续独立执行。

验收：最小 harness + 默认/定时/自定义运行策略的兼容矩阵；可选提示缺失不影响首步；确需 restart 时才按声明检查该能力；默认 harness 的控制行为保持正确。

## M01.1：身份与消息

| 当前类型 / 主键 | 实际含义 | 引用边界与审查结论 |
| --- | --- | --- |
| `ModelRef(backend_id, model_id, revision)` | 某后端上的模型版本引用 | 不自动证明服务实际加载的权重，也不区分相同权重的不同 agent 会话。当前 meta-agent 仍使用 `decision_maker` role。 |
| `Decision.decision_id` | 默认 meta-agent policy 提出的一次决策 | 属于默认 harness 的决策表达；依赖与信息来源有独立字段，不能直接视为所有外部 harness 的统一任务协议。 |
| `Directive.directive_id` | 发给 exploration 的不可变系统指令 | 与原 Decision 的映射由默认 harness 保存；允许扩展 payload，但不是 Actor 环境动作。 |
| `OperationCall` / `OperationResult` | 本地能力调用及其回执 | 异步调用还可返回 JobRef；终态可包装为 ExecutionReceipt。F02 已补修。 |
| `Feedback.directive_id` | exploration 指令的终态执行回执 | completed/failed/cancelled/partial 属于执行终态，不是反馈模型的解释。F01 已补修。 |
| `LabSpec` / `LabTask` | 固定目标环境及提交给它的任务 envelope | 显式保留 Lab、decision、task、幂等键及可选 run/agent/发起模型；当前复用 Directive 的已安装任务类型。 |
| `ExecutionReceipt` | 本地和 Lab 任务的共享终态观察输入 | 保留原始请求/结果及来源；不把工具指标推断为某候选的独立评测。 |
| `JobRef(job_id, backend)` | 后端作业身份 | 不与 directive ID 或 decision ID 混用；未知作业状态不能等同失败。 |
| `Candidate.candidate_id` | 提议的一组组件变更 | 不意味着已评测、已部署、已采纳；`base_version` 与 `parent_system` 分别表达训练基准和实验父系统。 |
| `SystemVersion.version` | data/model/harness 等组件的组合版本 | 组合版本与模型 revision 不等价；产物引用不代表内容已经下载或验证。 |
| `FeedbackLearningService` 及其 proposals | 对执行证据的解释和整理 | 与原始 Feedback 回执是两个层次；提案不等于执行事实或已应用的系统改进。 |

结论：核心身份分类保留，初审发现的校验不一致已补修。新增 envelope 显式关联 Lab、任务、决策和已知 agent 身份；未知身份保持为空。用户尚未验收这些逻辑，不能用改名或测试通过代替边界确认。

## M01.2：动作边界

已核对的内置路径：

| 动作层 | 当前表示 | 执行去向 |
| --- | --- | --- |
| Meta-agent 本地调用 | `Decision(kind='invoke', operation=...)` | decision tools，包含研究、查询、代码/工作区等已装配能力 |
| Meta-agent 提交系统任务 | `Decision(kind='explore', directive=...)` | exploration 接受 Directive，按 mode 选择 execute/SFT/RL/evaluate 等 handler |
| Lab 内 Actor 动作 | `ActionProposal(name, arguments, ...)` | Actor ActionSpace 和 environment |

SFT、评测、prompt 配置是系统指令，不要求先伪装成 Actor 动作。相关测试也覆盖了系统 SFT 不调用 Actor 动作选择/验证的路径。本子项在已审内置路径中未发现需要单独报告的缺陷。

用户定义的 decision 还包括完整代码任务和自动化：当前它们可能沿本地 invoke 执行，不一定进入 exploration。本次已让两类终态通过统一 observe 入口整理；默认 Runner 的派发仍沿现有接口，不能据此宣称所有任务都已迁移到 Lab 调度。

## M01.3：可替换性与资源责任

已验证：

- `Application` / `build_demo` 可注入任一侧或两侧工厂，组件通过 AssemblyContext 共享存储、产物、模型后端和 sandbox。
- 最小 harness 不需要暴露默认 `policy/state/memory`；现有测试实际装配了这样的替代实现。
- 独立 feedback service 通过 `FeedbackAdapter.model/evidence/publish/decision_ids/install` 接入；替代 harness 可以使用自己的 memory/context 布局。
- 默认 adapter 负责默认账本与知识视图的转换，选择和 compact 仍属于 harness；没有强制反馈服务继承默认 harness。
- 自定义 exploration 若要使用默认 decision 工厂，需要显式声明可执行 directives；装配不会从未知插件猜测训练或评测能力。

F03 已补修，最小 harness 可以使用定时/自定义运行策略。自定义组件的权限、清理与持久恢复仍须显式集成，不能宣称无条件替换。

当前责任边界：

| 事项 | 当前责任 |
| --- | --- |
| 共享存储、后端、sandbox 生命周期 | Application / AssemblyContext |
| 工厂自有资源 | 取得资源后用 `context.add_cleanup` 注册 |
| feedback service 生命周期 | 工厂接入会注册 service.close；直接调用 enable_feedback_learning 的调用方应显式管理关闭，不能仅凭安装就推定 Application 已接管 |
| 自定义 harness 执行授权 | 复用 authorized_space 或提供等效检查；README 已明确该责任，不能把插件代码本身当作被隔离的不可信代码 |
| 自定义组件快照/恢复 | 显式提供恢复适配；不支持时拒绝快照，避免假装已持久恢复 |

资源关闭仅核对实现和既有测试；未对真实后台模型调用进行压力或取消验收。直接安装后的关闭责任值得在后续生命周期审查中统一，但本次不将其列为已确认的额外故障。

## M01.4：Lab 与 feedback 的补齐范围

**基础契约和适配器已实现，默认调度尚未迁移。** `LabSpec / LabTask / Lab` 声明固定目标、能力、任务身份与生命周期；`ExplorationLab` 复用现有 exploration handlers。sandbox 仍是执行设施，不替代固定目标、能力清单和结果协议。

初审的接线缺口是只有 exploration 的终态交付触发整理。本次新增 `ExecutionReceipt` 和 `service.observe`：兼容旧 `receive_feedback`，默认 adapter 同时观察本地非只读操作的实际完成；异步提交不冒充完成，只读查询不自动触发整理，反馈读取即使被拒绝也不递归产生反馈。外部 harness/Lab 可显式提交回执和自己的证据快照，无需默认 state。

以下是当前实现及其边界，供用户逐项确认：

1. **任务 envelope**：`LabTask` 显式关联 decision、Lab、task、幂等键与可选 run/agent/模型。任务内容复用 Directive；接口不额外安装代码 agent 或训练算法。
2. **Lab 生命周期**：提交、推进、查询、取消、终态结果与确认；精确校验原始 directive 和回执身份。适配器任务索引仅进程内有效，持久恢复仍需显式集成。
3. **执行回执**：保留原始请求/结果和来源。共享三组有限指标校验；本地通用指标不推断候选/协议绑定。大输出在原始档案中可分页读回，模型输入可为明确标注的投影。
4. **反馈观察**：`observe` 接受统一回执，原始执行先记账，反馈整理后异步进行。重送同一回执不重做执行；同一身份改变结果会被拒绝。默认观察非只读完成，独立调用方可自行选择范围。
5. **产物消费**：context/memory 整理能力必须激活且实现可替换；轨迹默认开启、可关闭或替换，harness 修改可选；harness 消费视图并选择/检索/compact。轨迹转训练材料后续由 skill/规则定义，修改应用和 researcher 训练流程尚未实现。

用户随后明确共享权重以及可替换组件边界，已同步代码：默认 adapter 跟随当前 ModelRef；
有效反馈零提案也发布事实 Memory，失败或准入拒绝的事实 context 仍可独立读取；
默认 `view=trajectories` 索引所有已捕获片段，可关闭或替换；实际反馈请求/响应作为执行交付证据分别记录。当前 observer 没有捕获
原 meta-agent 的完整模型交换，索引明确缺失范围，不将片段宣称为完整会话或训练集。

跨 Lab 调度、通用代码研究环境、任务索引持久恢复留给后续模块。具体 feedback prompt、轨迹覆盖和三类产物 schema 留给 M07/M08/M09；具体上下文保护与增长策略留给 M06。
